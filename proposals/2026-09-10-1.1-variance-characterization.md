# Proposal: 1.1 Variance characterization and sample size

**Backlog item:** Wave 1, 1.1
**Author:** CTO
**Date:** 10 September 2026
**Status:** awaiting review with Hami (gate step 2)
**Claim intent:** experiment = Yes. Harness = Build only.

---

## What it is

For each AI engine, determine empirically how many independent runs of the same prompt are needed
before a measurement stabilizes within a stated tolerance, or establish that no practical number
exists.

The measurement in question is binary per run: did domain X appear as a cited source, and was brand
Y named in the answer text.

## Why now

Every other number the platform will ever produce depends on this one. Until sample size is
settled, "your visibility went from 40% to 55%" is not a claim we can defend, because we cannot say
whether 15 points is a change or noise. Every later experiment would inherit the same doubt, so
doing this second would mean redoing everything before it.

It is also the strongest SR&ED candidate in the file: there is no standard practice to fall back
on. Current tools in this category run a prompt once and present the result as fact.

## What is actually uncertain

1. Whether a stable sample size exists at all within a practical budget.
2. Whether it differs per engine, and by how much.
3. Whether it differs per prompt type (brand-name query vs open category query), which would mean
   there is no single n and the answer is a function rather than a constant.
4. Whether the underlying distribution is even stationary across the measurement window. If the
   engine's index or model shifts mid-sample, "converging on the true value" is the wrong frame and
   the method has to change.

Point 4 is the one most likely to break the whole approach, which is why it gets tested rather than
assumed.

## How we test it

- **Prompt set:** 10 prompts across two domains we own, hamitahm.com and homecalc.ca. Own domains
  only, deliberately: we know the ground truth, and no client is exposed to an experiment.
- **Prompt types:** half brand-name queries, half open category queries, so uncertainty 3 is
  testable rather than invisible.
- **Runs:** 30 per prompt per engine, executed in a compressed window, raw responses stored
  verbatim.
- **Analysis:** for each prompt, compute the running proportion as n grows. Bootstrap resample to
  find the smallest n where the estimate stays within a stated tolerance of the full-sample
  estimate. Compare that n across engines and across prompt types.
- **Stationarity check:** split each 30-run sample into first and second half and test whether they
  differ more than chance allows. If they do, uncertainty 4 is real and gets its own log entry.

## What done looks like

A documented number per engine with a stated tolerance and confidence, for example "n=12 gives
plus or minus 10 points for citation presence on engine A", **or** a documented finding that no
practical n exists and why.

Both outcomes are a result. The second is a worse product outcome and an equally good log entry.

## Size

Small on analysis, moderate on apparatus. The bulk of the work is the thin harness (backlog 0.1 and
0.2, minimal versions), which is explicitly Build only and not claimed.

## Open decisions, needed before any code

These are yours, not mine. The first one is not a detail.

**1. API or consumer surface?**

The engines' APIs and their consumer products are not the same system. The API generally does not
do the same retrieval and grounding that chatgpt.com or perplexity.ai does for a logged-in user.
So measuring the API cleanly may mean measuring something our customer never sees, while measuring
the consumer surface means automating a UI, which is fragile and sits against terms of service.

This determines whether the whole measurement is valid, so it is the decision, not a setup detail.
My read: start on APIs because it is stable and permitted, and treat "how far API results diverge
from the consumer surface" as its own later experiment rather than pretending the question does not
exist. But it is a real trade and you should make it.

**2. Which engines first?**

Recommend two, not six. Two gives a cross-engine comparison, which is the point, without
multiplying the apparatus cost by three before we know the method works.

**3. Where does the code live?**

This repo is the marketing site. The measurement engine should be a new repository. If you agree,
EXPERIMENTS.md moves there when it exists, per the note at the bottom of that file.

**4. Budget.**

10 prompts times 30 runs times 2 engines is 600 calls per full pass, and we will want several
passes. Small money, but it should be a number you approved rather than one I assumed.
